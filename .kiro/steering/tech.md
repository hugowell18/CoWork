# 技术规则

## 原则

Cowork 的技术规则只描述跨 spec 复用的协作机制，不提前规定某个具体运行时实现。

当前阶段只确认两点：

- 协作应由本地状态驱动，而不是靠复制 prompt 驱动。
- 具体队列、运行记录、事件模型、适配器等实现细节，必须在相关 spec 的 `design.md` 中再定义。

## 状态优先

本地状态是事实源。

通用规则：

- 规格阶段必须有可读取的状态记录。
- Codex 产出、Claude 评审、Codex 返工、Claude 接受、人工负责人最终裁决都必须能在状态中表达。
- Agent 执行结果必须写入 artifact。
- 重要决策和状态变化应有事件记录。
- Prompt 文件只能作为调试或降级通道，不能作为主事实源。
- 任何自动循环都必须能从本地状态恢复，不依赖聊天上下文。

## 跨平台原则

Cowork 必须能在 Windows 和 macOS 上使用同一套规格、状态文件和协作规则。

通用规则：

- 规格文档不得依赖 Windows 专属路径，例如盘符路径。
- 持久化状态中的路径应优先使用相对项目根目录的路径。
- 如果任务卡、artifact 或 loop 文件确实需要记录某台机器上的真实外部路径（例如某个 spec 协调的源数据库实际只存在于一台 Windows 机器上），必须明确标注这是"环境事实"字段，不能当成可移植默认值写进规格文档的通用示例或说明性 prose 里；可移植的持久化引用（分区路径、artifact 路径等）仍必须使用项目相对路径和 `/` 分隔符。
- 需要落盘的路径格式、路径分隔符、大小写规范和编码规则必须在具体设计中说明。
- 核心命令应优先使用 Node.js 或其他跨平台入口，不把 PowerShell、cmd、bash、zsh 的某一种作为唯一执行方式。
- 文档里的命令示例必须避免 shell 特有的重定向陷阱，例如未加引号的 `<placeholder>`。
- 文件锁、原子写、rename、delete、打开句柄冲突等行为，在 Windows 和 macOS 上差异明显；具体设计必须显式处理。
- 文本文件默认使用 UTF-8；设计阶段必须说明是否允许 BOM、CRLF/LF 差异，以及解析器如何容错。

## 规格状态

每个 spec 至少包含：

```text
.kiro/specs/<spec-name>/
  requirements.md
  state.json
```

后续文件只能按门禁推进：

```text
requirements.md -> design.md -> design review loop -> tasks.md -> tasks review loop
```

`state.json` 至少记录当前阶段和人工确认状态。

## 循环式协作

目标协作方式是循环式，而不是一次性 prompt 式。

共通循环概念：

```text
观察本地状态
判断是否允许推进
执行当前角色允许的动作
写入 artifact 或事件
等待下一轮
```

具体要不要有 coordinator、queue、run 记录、CLI adapter，以及它们如何落盘，必须由设计阶段决定。

## 锁机制

锁机制只定义通用规则，不定义具体业务资源。

规则：

- 资源名称由具体 spec 或 task 定义。
- task 需要资源时，必须先检查是否被其他运行持有。
- task 禁止资源时，即使资源未上锁也不能使用。
- 锁应记录持有者、资源名、开始时间、过期时间和原因。
- 过期锁可以被报告，但不应被静默忽略。

## 最小协作状态

在没有 `design.md` 和 `tasks.md` 之前，`.ai-coord` 只保留最小状态目录：

```text
.ai-coord/
  locks/       资源锁
  events/      事实事件
  artifacts/   输出物
```

其他运行时目录，例如队列、任务状态、运行记录、收件箱提示、脚本日志，都必须等设计阶段确认后再创建。
