# 需求：数据重量控制

## 状态

`draft`

这份文件等待人工负责人确认。在人工负责人确认这些需求之前，不要创建 `design.md`、`tasks.md`，也不要创建可执行任务。

## 背景

量化交易工程正在积累越来越多的市场数据。当前方向是：不要把 DuckDB 当成唯一的长期数据仓库。

核心原则：

```text
DuckDB 用来算，不用来无脑囤；Parquet 用来存，清单用来复现，数据集市用来跑策略。
```

本需求尤其要防止两类静默风险：

- 数据迁移后，查询结果和迁移前不一致，但策略仍然继续运行。
- 清洗标准层出现重复键或旧数据残留，质量门静默失败，信号跑在错误数据上。

## 需求 1：原始数据必须只追加

系统应把外部源数据落到原始层，并保持只追加、可审计。

验收标准：

- 当数据从外部源拉取时，原始输出能记录数据源、数据集和交易日期。
- 当原始数据写入时，数据本身或旁路元数据能关联 `source`、`ingest_run_id`、`fetch_time`、`usable_scope`。
- 当策略或回测需要市场输入时，默认不直接扫描原始数据。
- 如果原始数据需要纠正，应通过新的采集批次或显式覆盖修正记录表达，不做静默覆盖。

## 需求 2：清洗标准层必须定义主键、去重和幂等契约

系统应为清洗标准层定义可验证的键约定和重复数据处理规则，避免重复行卡住导入或污染信号。

验收标准：

- 标准日频表默认以 `(ts_code, trade_date)` 作为逻辑键；如某数据集不适用，必须在该数据集契约中显式声明替代键。
- 清洗标准层写入必须是幂等的：同一输入批次重复执行，不应改变最终有效结果。
- 写入清洗标准层时必须执行去重，去重规则必须写死为可实现策略，例如 last-write-wins、按 `source` 优先级、按 `fetch_time` 优先级，或由数据集契约指定。
- 质量门遇到重复键时，必须明确是自动按契约去重还是阻断；不得静默通过。
- 去重后的有效行数、重复键数量、处理策略和样例必须进入质量报告。

## 需求 3：清洗标准数据必须分区，并可被 DuckDB 查询

系统应把清洗后的标准表放到清洗标准层，并允许 DuckDB 在不把全历史导入主 DB 文件的情况下查询。

验收标准：

- 清洗标准日频表优先按月分区，避免按 `trade_date × symbol` 形成小文件灾难。
- 默认目标是每个数据集每月一个或少量 Parquet 文件；如果超过小文件阈值，必须进入压实流程。
- DuckDB 可以通过外部读取或视图直接查询清洗标准 Parquet。
- 历史分区可以迁移、压缩或归档，而不需要重写主 DuckDB 文件。
- 清洗标准表保留足够元数据，能追溯到原始数据源和采集批次。
- 对按 symbol 跨历史查询频繁的数据集，分区、排序或索引方案必须支持 symbol 裁剪或降低全表扫描风险。

## 需求 4：外部化迁移必须证明迁移前后结果一致

任何表从 DuckDB 内部表外部化为 Parquet 或 Parquet 视图前，系统必须证明迁移后查询结果与迁移前一致。

验收标准：

- 在抽样窗口和关键全量窗口上，对迁移前 in-DB 表与迁移后 Parquet 视图执行逐行一致性或校验和一致性验证。
- 一致性验证至少覆盖行数、主键集合、关键数值列、日期范围、空值分布和排序无关校验和。
- 一致性验证失败时，不允许 drop 原 in-DB 表，不允许把视图切换为默认生产查询入口。
- 一致性验证结果必须写入 artifact，包含验证 SQL、窗口范围、行数、校验和、失败样例和结论。
- 只有一致性验证通过，并且人工负责人批准后，才允许 drop 或归档原表。

## 需求 5：DuckDB 必须被视为查询引擎和按数据集定义的热层

系统应把 DuckDB 限制在元数据、小型参考表、当前研究数据集市和经数据集契约声明的热数据用途上。

验收标准：

- DuckDB 可以保留 instrument、trade calendar、board metadata、ingest metadata、quality-check metadata、近期热数据集市、result index、signal book、candidate book。
- DuckDB 不应作为全量分钟线、tick 数据、所有历史大宽表、所有中间研究产物的长期存储。
- 热窗口不能是全局常量；必须按数据集声明，并由预检强制检查。
- `bar_daily` 这类体量小但回看需求长的数据集，默认保留全历史可用，不得因全局热窗口被截断。
- `bar_minute` 这类高增长数据集应作为 Parquet 优先和热窗口治理的第一候选。
- 如果某张表超出约定的热层用途，应被标记为 Parquet 迁移或外部化候选。
- 系统可以区分热、温、冷三类数据层，但每类边界必须由数据集契约定义。

## 需求 6：回测必须通过可测量清单保证可复现

系统应通过清单记录回测输入快照，而不是把每次输入表都复制进 DuckDB。

验收标准：

- 正式回测记录数据快照引用、策略版本、代码提交标识或等价代码身份、生成时间。
- 清单必须标识 bar、daily basic、moneyflow、board 和其他策略依赖输入。
- 清单中每个输入数据集至少记录分区路径、行数、最大日期、校验和或采集批次集合。
- 回测结果可以追溯到当时使用的精确数据字节或等价可重建分区。
- 已接受的数据缺口或质量例外记录在清单或相邻质量报告中。

## 需求 7：每日同步必须增量化

系统应避免对可增量更新的数据每天做全历史刷新。

验收标准：

- 每日同步默认只拉取当天或缺口日期。
- 每日同步流程为：先写原始层，再写清洗标准分区，再做质量检查，最后刷新热数据集市。
- 全历史重建必须通过人工负责人明确批准的任务触发。
- 刷新近期数据集市不要求把全历史清洗标准数据导入 DuckDB。
- 如果同步发现重复键、缺口日期、质量门失败或旧数据残留，必须阻断或按已声明契约处理，不得静默继续。

## 需求 8：预检必须报告数据重量、迁移候选和策略风险

系统应提供预检报告，帮助判断哪些数据应留在 DuckDB，哪些数据应迁到分区 Parquet。

验收标准：

- DuckDB 可用时，报告包含 DuckDB 表行数。
- 能识别相关日期列时，报告包含日期覆盖范围。
- 报告识别大表或增长较快的表。
- 报告把 `bar_minute`、`moneyflow_daily`、`daily_basic` 标记为第一批治理候选。
- 报告必须显示每个数据集声明的热窗口，不能只显示一个全局热窗口。
- 报告必须标记因长回看、分位数、累计窗口、RSRS 等策略依赖导致不能截断的数据集。
- 如果 DuckDB 被锁定或不可用，预检应清楚报告该状态，而不是给出不清晰失败。
- Claude 刷新数据后，可以评审这份报告。

## 需求 9：Agent 协作必须尊重资源归属和锁的局限

系统应通过人工负责人批准的规格和显式锁来协调 Codex 与 Claude。

验收标准：

- Codex 先起草需求，并等待人工负责人确认后再进入设计。
- Claude 正在刷新数据时，Codex 不碰 DuckDB。
- Claude 做 DB 重验证前，必须持有或检查 `duckdb` 锁。
- 锁是协作型文件锁，不是数据库级强制锁；设计阶段必须说明如何避免不守规矩的进程或 UI 只读句柄阻塞写入。
- 写窗口内应要求相关 UI 暂停、切换只读连接，或通过串行化写入口执行写操作。
- Claude 评审输出问题发现和测试反馈，不静默修改 Codex 负责的实现。
- 人工负责人决定任何冲突、schema 变化、存储迁移或破坏性操作。

## 需求 10：外部化和 drop 必须可回滚

外部化、归档、drop 原表都属于高风险动作，必须先满足可回滚要求。

验收标准：

- 迁移前必须保留源表或可恢复备份，直到一致性验证通过并获得人工负责人批准。
- Parquet 分区必须能够重建被 drop 的表或等价视图。
- drop 原表前必须记录恢复步骤、恢复命令、源表位置、目标分区和一致性验证 artifact。
- 任何不可逆或难以回滚的操作必须单独列为人工负责人确认项。
- 迁移失败时，默认回到迁移前查询路径，不允许半切换状态继续服务策略。

## 需求 11：必须同时支持 Windows 和 macOS

系统应能在 Windows 和 macOS 上使用同一套规格、数据治理流程、预检报告和验收规则。

验收标准：

- 需求、设计、清单和 artifact 中的持久化路径应优先使用项目根目录相对路径，不应写死 Windows 盘符或 macOS 用户目录。
- 设计阶段必须定义路径规范化规则：持久化时如何表示路径，运行时如何解析为当前操作系统路径。
- 核心脚本和预检入口必须能在 Windows 和 macOS 上运行；如存在 shell 差异，必须提供等价命令或跨平台 Node.js 入口。
- 文件读写、原子写、临时文件 rename、删除、锁文件、打开句柄冲突等行为必须在设计中说明 Windows/macOS 差异和处理方式。
- 文本和 JSON 文件必须使用 UTF-8；读取器应能容忍常见换行差异，是否容忍 BOM 必须在设计中明确。
- 数据集名称、分区目录、表名和 artifact 名称必须避免仅靠大小写区分，防止在默认大小写不敏感文件系统上冲突。
- Parquet 分区路径和回测清单必须在 Windows/macOS 间可移植；不得把本机绝对路径作为唯一快照引用。
- 预检和一致性验证报告必须记录运行平台、路径解析结果和关键工具版本，便于跨平台复现。

## 实施分期

这些需求不得一次性合并成一个大设计批次。后续 `design.md` 必须按低风险、早出价值的方式分期设计和交付。

### P1：零风险预检与增量同步可观测性

目标：先暴露现状问题，不迁移、不 drop、不改写历史数据。

覆盖需求：

- 需求 7：每日同步必须增量化。
- 需求 8：预检必须报告数据重量、迁移候选和策略风险。
- 需求 11：必须同时支持 Windows 和 macOS。

验收重点：

- 预检报告能快速暴露覆盖异常，例如某数据集只覆盖少量股票、日期缺口、重复键、旧数据残留。
- P1 默认只读或低风险写入 artifact，不执行外部化迁移、不切换查询入口、不 drop 表。
- P1 必须在 Windows 和 macOS 上都能运行或给出明确的等价运行方式。

### P2：Raw/Clean 分层与 Parquet 落地

目标：建立原始层、清洗标准层、分区 Parquet 和质量门，但任何迁移必须带一致性和幂等验收。

覆盖需求：

- 需求 1：原始数据必须只追加。
- 需求 2：清洗标准层必须定义主键、去重和幂等契约。
- 需求 3：清洗标准数据必须分区，并可被 DuckDB 查询。
- 需求 4：外部化迁移必须证明迁移前后结果一致。
- 需求 10：外部化和 drop 必须可回滚。
- 需求 11：必须同时支持 Windows 和 macOS。

验收重点：

- Parquet 落地必须避免小文件灾难。
- 清洗标准层必须先钉死逻辑键、去重策略、幂等写入和重复键质量门。
- 外部化前后必须通过一致性验证；验证失败不得切换查询入口，不得 drop 原表。

### P3：热层治理与回测复现

目标：在前两期质量和迁移基础稳定后，再收紧热层策略和回测可复现清单。

覆盖需求：

- 需求 5：DuckDB 必须被视为查询引擎和按数据集定义的热层。
- 需求 6：回测必须通过可测量清单保证可复现。
- 需求 9：Agent 协作必须尊重资源归属和锁的局限。
- 需求 11：必须同时支持 Windows 和 macOS。

验收重点：

- 热窗口必须按数据集声明，不得用全局常量截断策略需要的历史。
- 回测清单必须能定位到当时的数据字节或等价可重建分区。
- 锁、写窗口、UI 只读句柄和跨平台文件行为必须在设计中明确。

## 当前需求决策

1. Spec 名称暂保留 `data-weight-control`；如后续需要更通用检索名，可在需求确认前改为 `data-tiering` 或 `data-lifecycle`。
2. 热窗口按数据集声明，不设全局 3 个月或 6 个月常量；`bar_daily` 默认保留全历史可用。
3. `bar_minute` 从一开始就作为 Parquet 优先候选。
4. `daily_basic` 可以考虑 DuckDB 基于 Parquet 的视图查询；`moneyflow_daily` 必须先证明分区、排序或裁剪策略不会导致常见 symbol 跨历史查询全表扫。
5. 下一阶段只创建 `design.md`，不提前创建 `tasks.md`；设计必须按 P1/P2/P3 分期，不允许把全部需求一次性塞进一个大设计批次。
6. 设计必须把 Windows/macOS 跨平台作为一级约束处理，不允许把某一个操作系统的路径、锁或 shell 行为当作默认前提。
